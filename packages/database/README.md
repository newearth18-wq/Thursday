# @jupiter/database

SQLite persistence for Jupiter Core (SET 1), built on `node:sqlite` — part of
Electron's Node.js, so there is no native module to build or ship. It runs only
inside the Jupiter Core utility process.

```ts
const { database, migration, preMigrationBackup } = await JupiterDatabase.open({
  path: '<data folder>/jupiter.db',
  backupDirectory: '<data folder>/backups',
  logger
})
database.transactions.run(() => {
  database.settings.put('logging.level', 'info', actor, now)
})
```

## What it guarantees

- **Configuration checked on open:** WAL journal, `synchronous=FULL`, foreign
  keys on. A file that fails `quick_check` is reported as `DATABASE_CORRUPT` and
  left untouched.
- **Migrations** (`src/schema.ts`) are applied in order, each atomically, and
  recorded with a sha256 checksum. Opening refuses a database created by a
  newer Jupiter (`DATABASE_SCHEMA_NEWER`) or whose applied migrations no longer
  match the code (`DATABASE_MIGRATION_MODIFIED`,
  `DATABASE_MIGRATIONS_INCONSISTENT`). An existing database is backed up before
  it is migrated.
- **Transactions** (`transactions.run`): `BEGIN IMMEDIATE`, savepoints when
  nested, rollback on any thrown error, after-commit hooks that never run for a
  rolled-back transaction. Async callbacks are refused, so a transaction can
  never stay open across an `await`.
- **Append-only records:** triggers refuse UPDATE and DELETE on `events` and
  `audit_log`.
- **Backups** (`database.backup(reason)`): online copy with progress and
  cancellation, integrity and schema check of the copy, then an atomic rename;
  only Jupiter's own backup files are pruned.

## Repositories

`settings`, `events`, `audit`, `serviceHealth` implement the ports declared in
`packages/core/src/ports.ts`; Jupiter Core depends on those interfaces only.
Every row read back is validated against `packages/contracts`: an invalid event
row is reported and skipped (the rest of the log stays readable); the other
repositories raise an error rather than return an invalid value.

## Changing the schema

- Add a **new** migration at the end of `JUPITER_MIGRATIONS`. Never edit or
  reorder one that has shipped: existing databases would refuse to open.
- Keep tables `STRICT` with CHECK constraints for enums and JSON columns.
- The upgrade test uses `test/fixtures/schema-v1.sql`, generated by
  `test/fixtures/generate-schema-v1.ts` from migration 1 only. When a later
  migration ships, add a fixture for the version before it.

## Tests

`packages/database/test/*.integration.test.ts` run against real SQLite files:
migrations (new database, v1 fixture upgrade, refusals), transactions,
**crash safety** (a separate process is killed with SIGKILL in the middle of a
transaction and of a migration; the database must reopen intact), backups,
event storage and the event bus with per-Mission ordering.
